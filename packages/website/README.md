## Website design

`app/site.css` holds the website's shared page widths, edge fades, typography, navigation, and card styles. All routes use `SiteLayoutShell`; content pages use the shared containers instead of supplying an opaque page background or space for a sidebar. `/editor/[game_id]` uses the full viewport with its own header and a link back to the game. Both Inter and Geist Mono load from local font assets.

`--site-header-height` controls the header, the available page height, and sticky docs navigation at each breakpoint. Anchor targets use `--site-anchor-offset`, which adds 16px to that height. The shared classes in `lib/siteNavigation.ts` apply it to homepage, docs, and Markdown anchors; the docs scroll spy reads the resulting scroll margin.

Same-page fragment links use Next's `Link`, including blog footnotes and the API contents and type links. Plain `<a href="#...">` jumps create history entries without Next's route state, so Back can change the URL without restoring the page after navigating away.

Below 1024px, both header navigation groups move into the hamburger menu while account controls remain visible. The menu button and navigation visibility share one breakpoint in `app/site.css`. Desktop navigation links have 40px gaps, with 48px between groups and 24px between account controls.

Capitalize every word in website page titles, section headings, and dialog titles, including short words such as A, An, Of, and To. Keep brand names, code identifiers, usernames, and creator-supplied game titles in their original casing. The homepage hero uses the approved sentence-case copy: “Make fun games.” The whole headline uses the normal text color with no forced line break.

Game images and names align with their grid edges, so section headings, Explore Games links, and directory controls share the same left and right edges. Card hover padding extends outside those edges, with 30px between image columns.

The `--game-thumbnail-ratio` variable controls game cards, content-card artwork, and game-detail images. `lib/gameRowLayout.ts` keeps responsive image sizes and the grid's maximum width. `GameDirectory` places a compact Search field to the right of the title, with Recommended, Top, and Recent underneath as plain links without separators. The controls stack below the title on smaller screens. Recommended shows the games people are playing, then the 5 newest games, then Top Games in one continuous grid without subheadings or duplicate games. The homepage shows My Games, then Recommended with an All Games link. Search covers every game in these collections and removes duplicates. Game cards open the game detail page, where the Play action lives. Splash thumbnails use their original square dimensions and placement, independently of the shared card ratio. The header surface fades in after scrolling with a hard lower edge, and the brand folds only while hovered. Cards use a padded gray hover surface, with the player count to the right of the title. The homepage textarea grows with its content using CSS `field-sizing`. The home page `/` redirects to `/create` (not permanently), and All Games lives at `/games`.

Game grids render all supplied cards and use native browser lazy loading for thumbnails. Each image appears as soon as it loads, independently of the other images. Each homepage section keeps its eight-card preview (two rows at four columns).

Asset detail previews show animation buttons to the right of the canvas, with play icons and a highlight for the selected animation. Labels wrap within the animation column on narrow screens.

Terms and Privacy use numbered Markdown headings with separate body paragraphs. Both Markdown renderers preserve the starting number of ordered lists so lists can resume after other content.

From the repository root, run `node --test tests/website_*.test.ts`. From `packages/website`, run `npx tsc --noEmit --incremental false` and `npx next build --webpack --experimental-build-mode compile` to check compilation without starting a server or deploying.

`lib/useRefState.ts` returns `[ref, setState]`. Call `setState(value)` to update `ref.current` immediately and request a render. The ref and setter stay stable across renders. Values, including functions, are stored directly. Use it only to replace an existing state and ref pair, as in prompt submission and optimistic likes. The hook tests use React DOM in jsdom without starting a server.

Creating a game stores its metadata and any initial homepage prompt in one transaction. Manual creation starts with no chat messages; the first published world is version 1.

Website Create Game, manual New Game, and Edit open `/editor/[game_id]`. Creation reuses the existing website actions. The editor page accepts the creator’s login or the game’s current invite link, then calls the website's `/api/edgegap-editor/start-editor-server/:gameId` route to find or start the game's Edgegap container. The browser talks directly to that container for AI chat, world previews, and playtest controls. `GET /editor-server-chat-stream` on Node sends the saved chat snapshot followed by shared message updates. `/editor-server-websocket` takes the browser's `Bearer <login token>` or `Invite <invite token>` credential as its first message, then sends the initial `EditorState` JSON followed by binary `EditorServerDelta` batches. After its credential, the page sends a short message on that socket whenever the person does something, at most every 30 seconds, which keeps the editor from pausing. A paused editor closes the socket with its reason, and the page shows it with Start editing. The shared state contains the world (including scripts) and `editor_status` (chat and user-playtest running flags). The browser applies world batches through Rust/WASM and updates the Explorer, Properties, script tabs, and scene together. Property and script edits travel back through `/editor-client-action` as they are typed, one request per user action. Undo and redo belong to the editor server: `POST /editor-history/undo` and `/editor-history/redo` apply a step and broadcast the result like any other edit. World setters and worker lifecycle changes trigger publication without polling. Scene updates reuse the renderer and load newly referenced assets while drawing continues. Chat streams directly from Node, and `/chat-interrupt` cancels a reply. Add Player opens a separate desktop process with the playtest address and a one-use join token in its deep link.

Shift-click or Command-click (Ctrl-click on Windows) toggles object selection in the Explorer and viewport. Every selected object is attached to the next chat message. Properties shows the intersection of the selected objects’ fields, with Mixed for differing values. Entering a value sets it on all selected objects; changing a vector or rotation component preserves their other components. Modifier-clicking an already selected rigid group toggles that group; ordinary viewport clicks still drill into its children.

`StoredWorldRenderable` holds the stored world and its parent lookup. Each server batch updates only the changed objects in the stored world, then rebuilds the full `RenderSnapshot`. The browser reuses that snapshot between changes; there are no separate persistent render caches on the stored world.

The homepage keeps one pending prompt in `sessionStorage` only when redirecting to login. It restores that prompt on return and clears it after successful game creation, which also saves the prompt as the game's first chat message. The browser editor loads that saved message and submits it when the editor server is ready. Browser editing does not record a desktop action or issue desktop authorization. A blank desktop app launch opens the homepage directly. Desktop play stores no game recovery state. Desktop links support play, playtest, and blank mode; editor launch and browser recovery handoffs have been removed.

The editor header, chat panel, and viewport remain visible during startup. Playtest and chat controls stay disabled until the connection is ready; startup failures show a toast and leave a retry button in the viewport. Chat, playtest, and renderer errors also use toasts. Interrupted replies do not leave a persistent notice; active reply progress stays beside the conversation.

The viewport shows a centered game thumbnail up to 576px wide, with a pulsing overlay and the K logo tumbling in 3D over its center, through server and GPU loading. The loading mark reuses the existing logo geometry and tumble animation. A skeleton fills the background until the canvas is revealed after its first rendered frame. Games without a thumbnail retain the skeleton and loading logo. All loading animations respect reduced-motion preferences.

Browser render assets load independently. The editor starts drawing while downloads run; missing textures use the renderer's default textures and missing meshes are omitted until uploaded. Download, decode, and upload failures show an asset-specific toast without stopping the world. Pending and successful uploads are shared within a GPU context; failed requests are discarded so a later load can try again, with no automatic retry loop. Asset previews wait for all asset attempts to finish and still render if some fail. Unmounting cancels downloads without showing failure toasts.

Click or tap an object in the editor viewport to select it and reveal it in Explorer. A hit inside a rigid group first selects the outermost rigid group; further clicks drill into nested rigid groups and finally the hit object. Local groups do not add picking steps. Once inside a rigid group, clicks on siblings stay inside that group; entering an unrelated group starts at its outermost rigid group. Clicking the selected object again keeps it selected. Clicking empty space clears selection and resets drilling. Picking casts a ray through the displayed frame and intersects the rendered triangles, including skinned mesh poses, without running physics or contacting the server. Always-on-top geometry takes priority. The query uses geometric surfaces, so material texture alpha holes and transparent pixels within glyph quads are not excluded. Explorer expansion and arrow-key navigation preserve selection and camera position; automatic scrolling to a selected row happens only when selection changes. Clicks also focus the free camera and still select while movement keys are held, including when a key starts or repeats during the click. WASD moves forward/backward and sideways relative to the view; Q moves up and E moves down along the camera’s tilted up axis, keeping the desktop key bindings. Holding either Shift key slows WASD/Q/E movement to one fifth of its normal speed; releasing it restores normal speed. Dragging looks around, and scrolling or pinching moves forward/backward without changing the field of view. Left and right mouse drags use pointer capture: the cursor stays visible, dragging continues outside the viewport until release, and no pointer-lock notice appears. Movement remains limited by the screen edges. Mouse-look sensitivity is twice the original desktop camera's; touch gestures keep their existing sensitivity. Typing in chat never moves the camera. Camera position survives world updates.

The chat and right sidebar can be resized against the viewport. All three resize dividers use one thin line with a larger pointer hit area and support arrow-key resizing. On mobile the workspace panels stack vertically. The right sidebar restores the desktop Explorer and Properties panes with compact tree rows, consistently padded headings, and plain dropdowns. Explorer and the chat selection chip share React Icons equivalents of the desktop object symbols, defined in `EditorObjectIcon.tsx`. Skeletal types share a bone color, property animations and keyframes share pink, PropertyAnimator uses light blue, and primitive shapes share a red cube. Mesh uses assets’s `GiMeshBall` icon. Material uses `IoMdImages`, and Clock is gray. Skeleton and SkJoint use the same bone outline and stroke width, with a filled interior for SkJoint. Search finds objects by name or exact ID and shows their ancestors; expanding folders and selecting objects also work with the arrow keys and Enter. Drag the divider to resize the two panes. Single-clicking an Explorer row selects it without moving the camera. The selected row has a stronger blue background, and all visible descendants have a lighter blue background, including in search results. Double-clicking the row frames the object and its visible descendants while preserving the camera angle; double-clicking the same row again reframes it. Keyboard selection, property reference buttons, and folder expansion do not move the camera. Framing uses the rendered primitive and mesh bounds and the current viewport aspect ratio. Objects without rendered geometry leave the camera in place. Properties include names, shapes, transforms, physics, visual settings, materials, and object references. Reference buttons select the target in Explorer. Selection draws the desktop blue silhouette outline around the object and its rendered descendants, including meshes and labels. The outline is a renderer overlay and is excluded from screenshots. Properties use compact label/value rows with embedded X/Y/Z markers and separate Shape, Transform, Movement, and Physics sections. Every property stays in a two-column table layout, with its field name aligned to the first control line on the left and its input on the right, even when the inspector is narrow. Rows and group headings share a 28px minimum height and a consistent 6px vertical gap, including nested properties. Read-only Type and ID use the same row component as editable fields. Group wrappers add no padding or margins. Property fieldsets contain their hidden accessibility labels so selecting an object does not add page overflow below the editor. Color properties show only a color picker, with no RGB inputs. Property inputs and dropdowns cap at 6rem and shrink with the sidebar; vector components use this cap individually, while text areas can grow to 20rem. Property controls use shadcn Input, Textarea, Checkbox, Button, and Select components, with custom dropdown menus and quiet triggers. Optional fields show their name once, with the enable checkbox beside the value; optional objects keep one heading above their child fields. Numbers display up to three decimal places (or three significant digits for tiny values), reveal full precision on focus, and never write rounded display values back just from focusing and blurring. Numeric text stays unrestricted while typing; valid values immediately update the world, clamped to the field's allowed range, while blur or Enter formats the field. Integer fields round to whole numbers; other fields retain precision without snapping to the step size. Empty or non-finite input stays local until completed, and Escape discards that unfinished text without undoing valid edits already applied. Decimal inputs provide native steppers and arrow-key behavior with a step of 0.05 in displayed units. Storage limits too large to represent that step are excluded from the native step base, while commit still clamps to the full schema range. Integer fields, including asset IDs, use numeric text entry without steppers and apply rounding and clamping while typing. Rotations display XYZ degrees and keep Rust's quaternion storage format.

The workspace's React reducer owns the editable world and selected object IDs. The chat composer has no outer top spacing above its box. Messages have 24px horizontal padding to sit inside the composer's edges and 12px bottom padding that scrolls with the conversation. The chat uses `use-stick-to-bottom` to follow streamed output and content resizing while the reader is at the bottom. Scrolling up pauses following; scrolling back down or pressing Scroll to latest resumes it. Only the message pane scrolls, without moving the page or composer. Its bottom row shows one named chip per selected object beside Send. Removing a chip deselects that object in the chat, inspector, and viewport. Sending a message includes the IDs, names, and types of all selected objects as text context for the AI. Property edits preview immediately and are sent to Rust through `POST /editor-client-action`, using the same ordered request queue as script saves. One action is one undo step however many objects it changes, and each request carries an `x-editor-session` header naming this tab, which is the undo history's idea of who did what. The browser sends at most one action every 100 ms; a field edited again while it waits keeps only the value typed last, so live typing does not send a request per keystroke. The server applies the action and broadcasts its authoritative result to all connected browsers; incoming state replaces local property previews. Saving happens on the editor server on its own, so there is no Save button and no save request. Removed objects clear their selection. Existing playtests remain snapshots until restarted. The inspector schemas describe StoredWorld JSON directly, independently of the flattened script API; schema tests check the Rust object variants and fields. The Rust/WASM decoder checks the editor sync protocol version once in the initial `EditorState` snapshot on `/editor-server-websocket`. Subsequent `EditorServerDelta` batches omit the version and contain world changes and the current `editor_status` flags for chat and user playtests in every batch. Rust world setters and worker lifecycle changes trigger updates without polling; AI SDK messages use Node's shared chat event stream. Reloading reconnects with a fresh snapshot. Deploy the website/WASM and editor server together.

Leaving the editor always warns, without inspecting whether anything is unsaved: other clients and the AI edit the same world, so the browser cannot tell. The warning covers closing or reloading the page, the header's back link, and browser Back. Chrome only shows its own unload dialog once the page has been interacted with, so closing an untouched editor does not prompt. Publish and the thumbnail button are the only header actions that write. Publish waits for this browser's edits, then calls `POST /publish-game`, which uses the existing Rust publication and thumbnail capture. The thumbnail button sends the current view to `POST /set-fallback-camera`. Script text streams to the server while it is typed, exactly like property edits, so there is no script save step and no Cmd+S. Chat input stays local; world changes, running flags, and chat messages are shared. The creator and anyone holding the current invite link can share the editor.

## Dev website and editor

Clicking a Script in Explorer opens a closable Monaco tab beside World. Tabs are keyed by object ID, so renaming a script does not lose it or open a duplicate. Switching documents preserves each open script’s cursor, scroll position, and undo history, and keeps the world canvas mounted. Closing a tab retains its React draft for reopening; removing or changing a Script object clears its tab and draft. In Monaco, Cmd/Ctrl+K followed by W closes the active script, as does the Close Script command. Cmd/Ctrl+W is also bound when the host delivers it, but normal Chrome tabs reserve that shortcut for closing the browser tab; intercepting it requires fullscreen keyboard lock. The tab strip is hidden when only World is open. Script drafts are separate from the rendered world, so typing does not rebuild the scene. Save, Cmd/Ctrl+S, and Monaco’s Save Script command persist the active script through Rust to the unpublished editor world. Failed saves retain local drafts; the last applied edit wins, and typing during a save keeps the newer text dirty. Property edits and saved scripts both propagate through the central sync layer. Monaco’s TypeScript worker provides completions, hover types, signature help, and local syntax/type diagnostics. When scripts open, the browser reads the generated game API declarations, runtime globals, JSX dependencies, and compiler options from authenticated Node `GET /get-script-types`. All world scripts, including unopened scripts and local drafts, participate in relative imports through their hierarchy paths. Typing does not send diagnostics requests to the server. The worker runs independently after declarations arrive; server diagnostics remain available to AI tools. The status bar counts local errors and warnings. Declaration, worker, request, and property validation failures appear as toasts. Editor text fields, search, chat, colors, and dropdowns disable browser autocomplete and carry LastPass ignore hints where applicable. Monaco’s generated inputs, including Find/Replace, receive the same hints when created; this leaves TypeScript completions enabled. Password managers can still choose to ignore these hints. Saving is independent of diagnostics and does not publish a game or alter an existing playtest.

Before the first browser-editor run, apply `0042_browser_editor.sql` with `npm run drizzle-migrate` from `packages/website`. The dev editor uses the hosted database too, so its draft table and chat columns must exist before opening a game.

Run `./scripts/run_website.sh` from the repository, or `scripts/windows-versions/run_website.ps1` on Windows. It builds the script declarations, Rust editor, desktop client, and browser renderer, then opens the development services on fixed ports:

| Service | Port | Starts |
| --- | --- | --- |
| Next.js website and website API routes | 3000 | With the script |
| Rust editor_server API | 8080 | When a game is opened |
| Node AI SDK/TypeScript API | 8081 | Alongside Rust |
| User playtest server (UDP) | 5000 | When Playtest is pressed |

Pressing Playtest starts the server and automatically opens the first player; Add player opens additional players. In dev, each launch runs the `client` binary built alongside the dev editor with `--open-separately` and its one-use playtest link. The existing Rust `/playtest/add-player` endpoint launches it directly and returns 204, so dev playtests do not use the installed app's URL handler. Hosted editors still return a deep link for the browser to open. If opening the first player fails, the server stays running so Add player can retry.

Visit `http://localhost:3000`. Next.js keeps its dev editor in memory across hot reloads. One game editor runs at a time; opening another game saves and closes the previous editor. Each editor has a distinct URL on the fixed API port, so old tabs cannot accidentally edit the new game. Ctrl-C shuts down Next.js; closing its pipe tells Rust to save and shut down the editor and playtests. Supabase, asset storage, and AI providers remain hosted. Normal published-game Play keeps its existing hosted flow.

Configuration uses the website's existing files through [Next.js environment loading](https://nextjs.org/docs/pages/guides/environment-variables). The editor reads its Bedrock API key, `AWS_BEARER_TOKEN_BEDROCK`, and its other secrets from `.env.local`, which git ignores and `infisical export` writes (see README_SECRETS.md). `.env.local` also points the site URL at localhost. The launcher supplies ports and a temporary internal credential; it uses the same AI model and region as the editor image. Dependencies come from `./scripts/install_deps.sh`.

Dev editor processes are tracked in memory on this computer; the production starting/running editor tables only track Edgegap deployments. Game drafts and chat still use the configured Supabase database. Use a direct or session-pooler database URL for chat’s database locks.

## Editor hosting API

The creator's editor header includes Share. Opening it creates a persistent, random invite token only when the game has no active link; subsequent opens return the same link. Rotate replaces the token. Hide clears it and closes the modal; opening Share again creates a new link. The raw token is stored in `editor_share_auth(game_id, invite_token)`, independent of editor deployments. No row or a null token means sharing is off. Apply `0043_editor_share_auth.sql` through the existing migration workflow before using these controls.

The modal calls the `updateEditorShare(gameId, action)` Server Action in `app/server-actions/editor-share.ts`. Next.js handles the request; the action reads the website login, validates the input, and checks ownership in its database mutation. It returns `{ inviteToken: string | null }` on success or `{ error: string }` for a missing login, invalid input, or a game the user does not own. The modal displays those messages directly and uses a generic message for unexpected failures:

- `create` creates a link or returns the existing one.
- `rotate` replaces the link.
- `hide` turns sharing off by setting the token to null.

An invite link opens `/editor/<gameId>?invite=<token>` without requiring login. The page and startup route use the same database authorization check, so a valid invitation can also restart an editor after shutdown. The creator continues using their login, even when opening an invite link. Guests send `Authorization: Invite <token>` to both APIs and the same credential as the first world WebSocket message. Every request checks the current token for that game. Chat streams close after each completed, interrupted, or failed turn, and after at most fifteen minutes if no turn ends. The browser reconnects through normal request authentication and loads the saved snapshot without resending its prompt. World sockets recheck access once a minute inside their receive loop. Revoked invitations fail these checks; creator access remains valid when invitations change. Requests already accepted and the shared AI turn can finish after revocation. The token stays out of shared world state and internal deployment credentials.

Guests can edit objects/scripts, use chat, Save, Publish, and control playtests. Their AI usage belongs to the creator, and their playtest players are named Guest with separate player IDs and join tokens. Only the logged-in creator sees Share or can call its Server Action. New games accept an empty chat history so their first message can be sent. No browser database access or additional auth endpoint is introduced.

Editor hosting lives in this website. There is no separate Render service, API package, or editor API hostname.

- `POST /api/edgegap-editor/start-editor-server/:gameId` accepts the creator’s website session or the game’s current invite token, and finds or starts the editor. It returns 202 while starting, then `editor_url` and `chat_url`. The browser uses these container URLs directly for editing and chat.
- `POST /api/ai-mcp/:gameId?invite=<token>` is the MCP server (`@modelcontextprotocol/server`, stateless, so each request builds its own server) for an AI outside kube.new. The Share modal shows it under the link for people. It checks the invite, then reaches the editor the way Node does, through `/local-only/tools` and `/local-only/run-tool-call` with the deployment credential. It uses the address in `running_editor_servers` so tool calls do not ask Edgegap, and opens the editor the way the editor page does when there is none or it does not answer. Connecting needs no editor; the tool list and tool calls wake it. The route adds `read_system_prompt`, which returns a short note followed by the editor's own instructions. It also adds the file tools for the Import and Download tabs, which answer with a curl command for the AI's own shell once the editor answers on `/health`. `MCP_ONLY_TOOLS` in `mcpTools.ts`, next to the route, lists every tool that only an outside AI gets.
- `POST /api/edgegap-editor/webhooks/ready`, `/error`, and `/terminated` receive deployment lifecycle callbacks using the same webhook secret as normal game servers. Readiness still requires Rust's health check before promotion.

`lib/editorServers.ts` preserves the allocation transactions and deployment-scoped cleanup. It uses the website's existing database connection. `lib/devEditorServer.ts` owns the single dev process; it never uses production hosting tables. Rust keeps responsibility for idle shutdown, final world saves, and stopping its Edgegap deployment.

For deployment, configure `EDGEGAP_EDITOR_APPLICATION_NAME`, `EDGEGAP_EDITOR_VERSION_NAME`, and `EDITOR_SERVER_SECRET` on the website. The website passes the editor secret, with the editor's other secrets, to each editor it starts (see [README_SECRETS.md](../../README_SECRETS.md)). The application/version defaults remain `kube-new-editor-server` / `prod` in the website's checked-in environment. Reuse the website's existing `EDGEGAP_API_TOKEN`, `EDGEGAP_WEBHOOK_BASE_URL`, and `EDGEGAP_WEBHOOK_SECRET`; the base URL must point to this website.

Deploy the website and updated editor image together, then retire the old Render hosting service. No database migration is needed for this move. The obsolete `NEXT_PUBLIC_EDITOR_API_URL` is no longer read. Dev mode does not need Edgegap credentials; use `./scripts/run_website.sh` to supply the child process configuration.
