# Editor API (Edgegap)

Each game's Edgegap container runs Rust `editor_server` and its Node child. Both APIs accept the creator's login or the game's current invitation. Rust owns and persists the editable world; Node owns AI SDK messages and streams.

`game_types/src/editor_sync.rs` defines `EditorState`, the state shared between the browser and editor server: `world: StoredWorld` (including scripts) and `editor_status` (the chat and user-playtest running flags). Runtime handles, browser selection and unsaved script drafts, and AI SDK messages are separate.

The authenticated `/editor-server-websocket` sends one JSON `EditorState`, then binary `EditorServerDelta` batches. `src/editor_sync.rs` reads the full state, drains changes once for all subscribers, and accepts `EditorClientDelta` edits. `EditorServer::connect_client` and `EditorServer::broadcast_changes` own the world lock so connecting clients do not miss world changes. Every batch includes the current `editor_status`; `EditorSync` has no separate mutex or record of which status it last sent. World setters wake publication through `Notify`; worker lifecycle changes use one watch channel. The Rust/WASM decoder validates `protocol_version` once in the initial `EditorState`; binary deltas omit it. `BrowserEditorWorld::apply_deltas` handles wire decoding and status output; `StoredWorldRenderable` applies only decoded object changes and script sources. A client that falls behind is disconnected and must reload for a new snapshot.

The browser sends property edits and script saves through `POST /editor-client-action` with `{ description, deltas }`, where each delta is `{ objectId, section, path, value }`. One request is one user action, so an edit across several selected objects is applied, saved, and undone as one unit. `EditorServer` owns edit execution, saving, and publication; HTTP handlers decode requests and return responses. Browser edits hold the world lock only while they change the world; HTTP success means the edit was applied, and a background task writes it to the database shortly after. Their setters wake the same background publication loop as AI edits, which broadcasts after the lock is released. `EditorSync` interprets browser deltas, and `World` setters maintain references, derived state, and dirty tracking. The browser delta path and existing typed setters share `World::setObjectInfo`. Changes reach every browser, including the sender. The last applied edit wins. Browser requests are ordered; property edits preview immediately and incoming server state replaces those previews. Script text is sent while it is typed, the same as property edits. Undo and redo belong to the editor server, in `src/editor_history.rs`. It keeps one ordered log of steps plus a position per editing session: that session's steps before its position are done and the ones after are undone. `POST /editor-history/undo` or `POST /editor-history/redo` applies one step and returns `{ description, object_ids }` (`null` and `[]` when there is nothing to take); that browser selects `object_ids` so the change can be found. Applying a step is an ordinary world change, so it reaches every browser through the same broadcast as any edit, and it survives a browser refresh because the browser holds no history at all.

Every guest shares one invitation token, so the browser names its own editing session in an `x-editor-session` header and steps are attributed to that. One tab is one undo lane, for the creator and guests alike, so nobody's shortcut reaches anybody else's work.

A step is the list of values its cause changed, each paired with the value it replaced. Redo writes the step's own values and undo writes back what its last application replaced, so an undo after a redo gives back whatever that redo replaced. Nothing is inferred: `World` reports every object it changes through the same marks browser sync reads, and the history compares those objects with its own copy of the world (`src/editor_world_tracker.rs`) before and after every action, before every undo or redo, and at both ends of a reply. A changed field is one value, and so is anything whose shape changed, like a clock switching between playing and paused. A removal is one value holding the whole group that went, parent first, with the links other objects had into it, and an add is the reverse; a press that removes objects keeps the group it took, so pressing the other way brings back that version. A part of a rigid group keeps its place under its group, so moving the group changes nothing of the part's own. A value is written only where its place still exists: an object that is there, a shape the object still has, the group a part's place belongs to, a parent that exists and would not put the object inside itself, and an object the link points at. A link a removal cleared comes back only while that field is still empty. A press brings back removed groups first, then the links into them, then parents from the outside in, then every other value, and removes objects last. A press that changes nothing is passed over in the same press. A new step of a person's own drops whatever that session had undone, and a keystroke continues its field's step while the field still holds what that step wrote. Every browser learns from the editor status whether its own session has anything to undo or redo, keyed by a hash of the session so no browser learns another's; the undo and redo buttons and shortcuts do nothing when there is nothing to take. The log is bounded by how much it holds as well as by how many steps it holds, counting a removed group once however many sessions share it; the newest step, and every step from the latest reply, always survive.

The AI never has steps of its own. Just before a person edits, undoes or redoes, whatever the AI changed since the last look is cut into steps, so their action comes after it; the rest is cut when the reply ends, which reads every object, so a change the World never reported is still the AI's. A change goes to every person who changed one of its objects themselves, including in steps they have undone, as a step marked with the reply's number. It goes below the steps they undid, so they can still redo them. Within one reply, such a step also takes the AI's removal of anything it needs in order to be undone: a parent or link target one of their objects left, or the parent of a group it brings back. Objects the AI created, and objects that only came back inside a group, are nobody's. A part the World moved to another group, or re-placed inside its group, only because a folder above it moved has not changed: its place goes with the folder's change, is not listed, gives nobody a step, and is written back only where the part is back in that group. The chat lists every object the AI touched in the reply, from its value just before the AI first touched it to its value now, leaving out objects that end as they began and objects a person was the last to take away; redoing the reply's own step counts as the AI's. Undo and redo work while the AI runs. The reply closes only once any tool still running has finished, so a tool finishing after Stop is still counted as the AI's, and browsers learn it has stopped only then. Beginning a reply also closes one whose end was never reported. The history lives in memory, so a restart starts it over.

Node reports whether a reply is active through authenticated `POST /local-only/chat-status`. Rust updates the user-playtest flag at its lifecycle boundaries. Node's authenticated `GET /editor-server-chat-stream` sends an initial history snapshot and then newline-delimited message updates to every connected browser. `POST /chat-message` accepts one user message and returns 204 once generation starts; `POST /chat-interrupt` stops the shared reply. The separate `/get-chat-state` endpoint has been removed. Playtest controls remain Rust commands; their resulting state arrives through the shared sync stream. The old world socket, separate status fetch, and script-specific save endpoint have been removed. Editor sync requires the browser/WASM and editor server to be deployed together.

Rust starts `node/` for AI SDK chat and TypeScript diagnostics. AI SDK owns the model/tool loop and UIMessage assembly. Node consumes its stream independently of browsers, checkpoints messages, and broadcasts complete message updates at those checkpoints and completion. Closing one browser does not cancel the reply; reconnecting reads saved history and joins subsequent updates. A slow subscriber is disconnected without delaying other subscribers. Node reads `GET /local-only/tools` and executes the original Rust tool registry through `POST /local-only/run-tool-call` with `{ name, arguments }`, which answers with the tool's result as one JSON value once the tool finishes. The AI chat also gets tools of its own from Node, for its Linux sandbox and its subagents (see [Which AI gets which tools](#which-ai-gets-which-tools)). When a tool needs script diagnostics, Rust sends the current script snapshot to Node's `POST /local-only/read-script-diagnostics`. This returns diagnostics only. Rust reads script text and filters tool results itself; text-only requests skip Node. The browser separately reads `GET /get-script-types` for the same compiler options and generated declarations, then runs its own Monaco TypeScript worker for completions and diagnostics without sending drafts for checking. These calls use loopback HTTP with the deployment token on the existing listeners; the `/local-only/` prefix describes intended callers, not network isolation. Node has no world persistence or hosting logic.

The [website hosting API](../../packages/website/README.md#editor-hosting-api) finds, starts, and tracks these containers. Each container handles its own shutdown.

Rust owns the editable world and runs the original `tool_registry`. Asset search, download, and publishing call Rust handlers directly. The header also exposes `POST /publish-game`; publishing invokes the same Rust publish tool without an AI turn. There is no save endpoint: every change to the editable world wakes a background task that collects changes for a second and then writes the world once, so browser edits and AI tools never wait for the database. Shutdown writes the world one last time. The game-settings tools call Rust database handlers directly, scoped to the container's game id; omitted fields stay unchanged and an empty description clears it. Changing visibility does not publish the editor world. The website's Assets page reads the same database through its own server-side helpers. User playtests and AI headless playtests take separate snapshots of that world. Screenshots are drawn by the editor server itself with wgpu (`src/screenshot.rs`), with a playtest player's GUI drawn over them by headless Chromium from the same page the desktop client shows, so no browser tab has to be open. Each one draws in its own short-lived `editor_server draw-screenshot` process that Linux kills first when memory runs out, so a failed screenshot returns an error instead of stopping the editor. The AI's `capture_screenshot` gives its own camera, and a publish thumbnail uses the game's fallback camera, which the browser's thumbnail button sets with `POST /set-fallback-camera` and the AI sets with `set_fallback_camera`. Publishing never changes it. A publish saves that screenshot as the game's `screenshot_uuid`. Until the game has an AI thumbnail, the publish also has Node redraw the screenshot with OpenAI's GPT Image as polished art with no text (`POST /local-only/generate-ai-thumbnail`), which Rust saves as `ai_thumbnail_uuid`. After that, publishing leaves the AI thumbnail alone, except for the first publish after someone uses the editor menu's Refresh AI Thumbnail (`POST /refresh-ai-thumbnail`), which redraws it from that publish's screenshot. The editor keeps that request only in memory. A game can be published at most once every 5 seconds. The website shows the AI thumbnail, or the screenshot when there is none, and the game page can switch between the two. On the Linux container the only GPU is Mesa's lavapipe, which draws on the CPU.

The browser can also add assets and files itself. `POST /asset-download` with `{ asset_id }` adds the item's latest version the same way the AI's `asset_download` tool does and returns `{ object_id }`. It is one undo step, `Add <name>`, for the session that asked, and it works while the AI is running because it does not take the tool lock. `POST /asset-import?kind=Mesh|Texture|Skybox|Sound&name=<name>&should_publish=true|false&asset_id=<id>` takes the raw file: a `.glb` of at most 8 MiB, a PNG, JPEG, or WebP image of at most 2048 pixels per side, or an Ogg Vorbis, MP3, WAV, or FLAC sound, and never more than 16 MiB. Sounds are stored as Ogg Vorbis, so the other formats are converted, keeping their sample rate and channels. Its data is stored as the game's creator and added the same way. With `should_publish=true` it is also published as an asset attributed to the creator: a new one, or with `asset_id`, that asset's next version. It returns `{ object_id, asset_id }`, with `asset_id` null when it wasn't published. Only a published model keeps its `.glb` as its source. `POST /asset-import-material?name=<name>&should_publish=true|false&asset_id=<id>` takes a multipart form with one image per map: `albedo` is required, and `normal`, `roughness`, and `metallic` are optional. Each image follows the same image rules, and the form may hold 64 MiB in all. The images become one Material, with the color map encoded as color and the others as data, then are added, published when asked, and returned the same way. The material blends when the color image has any see-through pixels, and is opaque otherwise. `GET /asset-download-source?asset_id=<id>` returns a model asset's saved source file, its `.glb` or a `.blend` from kube.new's older Blender tools, with its type as the Content-Type. Only the creator's models have one. The AI chat sends and fetches files through these three routes under `/local-only/`, with the deployment credential, and what it adds waits for the tool lock and belongs to its reply, like a tool's change, rather than being an undo step of a session. The browser downloads the world as a `.kube` file from its own copy, and `GET /download-world` returns the world as the editor holds it, for an MCP client, which has no copy. `POST /upload-world` takes the `.kube` file as its body and checks it before anything loads it (how deep its hierarchy is, transforms, shapes, and the camera), and is refused while the AI or another tool is running. `World::loadNewWorld` then replaces everything under the root, giving each uploaded object a new id. Uploading is the one change that clears the history, for every session. The world is saved at once; if that save fails, the upload still stands and the background save writes it later.

## Shared editing and saving

The creator and invited guests connect to the same editor and share world updates and chat. Creator requests use `Authorization: Bearer <Supabase token>`; guest requests use `Authorization: Invite <token>` without requiring a login. The world WebSocket accepts the same credential string in its first message. Every browser request checks the current game owner or invitation, plus the deployment record outside dev mode. Guests can edit, chat, save, publish, and control playtests. Chat usage is attributed to the creator; guest playtest players receive independent player IDs and one-use tokens with the name Guest.

The website's Share modal stores a persistent invitation in `editor_share_auth` and can rotate it or clear it with Hide. This requires website migration `0043_editor_share_auth.sql`. Only the creator can manage invitations through the website Server Action. Valid invitations can also start a new editor after shutdown. Chat streams close after each completed, interrupted, or failed turn, delivering their queued messages first. The browser automatically reconnects through normal request authentication and loads a fresh snapshot without resending its prompt. Subscriptions also expire after fifteen minutes so idle streams cannot stay open forever. Rust world sockets recheck access once a minute inside their existing receive loop. Revoked invitations fail these checks; creator access remains valid when invitations change. Revocation does not cancel requests already accepted or the shared AI turn. Invitation management adds no Rust or Node endpoints, and guests never receive the deployment credential.

Save and Publish first submit this browser's script drafts and wait for its queued property edits. Save persists the authoritative world to `game_editor_worlds`. Publish runs the existing version/thumbnail operation. Other clients' unsaved drafts and input remain local. No conflict resolution beyond the last applied edit is added.

Deploy the website/WASM and Rust/Node editor image together (editor protocol 10). Shared chat and Save/Publish do not require a database migration, new environment variables, or additional services.

The registry's tools are in `shared/src/api/protocol_for_chat/tool_registry.rs`, the AI chat's own tools are `CHAT_ONLY_TOOLS` in `node/src/helpers/chatTools.ts`, and MCP's own tools are `MCP_ONLY_TOOLS` in `packages/website/app/api/ai-mcp/[gameId]/mcpTools.ts`. The three file tools have the same names and inputs on both sides: the AI chat's read and write files in its sandbox, and MCP's answer with a curl command for the outside AI's own shell. Both reach the same editor routes.

## MCP

The Share modal also gives a link for an AI, with the same invite code as the link for people, so turning sharing off revokes both. An AI running outside kube.new, such as Codex or Claude Code, uses it to call the editor's tools, and the editor server runs them the same way it runs the built-in AI's.

- The AI chat's own tools, for its sandbox and its subagents, live in Node rather than in the editor's tool registry, so an outside AI never gets them. Subagents would run our own model on the creator's credits.
- What the editor lets a person do in its tabs but has no tool for is given to an outside AI as tools of its own, for example uploading a file to assets and downloading the world.
- The editor can't see inside an outside AI, so there is no lock between AIs and no limit of one AI at a time. Tools take turns on the tool lock, and between tool calls the last change wins, the same as when a person edits while the built-in AI works.
- The editor can't stop an outside AI.
- Each of its tool calls is a reply of its own in the history, so people can undo what it changed on their objects, one call at a time.

The link is the website's MCP route, `/api/ai-mcp/<gameId>?invite=<code>`. It checks the invite, then calls the same `GET /local-only/tools` and `POST /local-only/run-tool-call` that Node calls for the built-in chat, with the deployment credential. The route is what makes an outside AI different: it gives the AI a short note and tools of its own. The AI reads the system prompt, after that note, through the route's own `read_system_prompt` tool rather than the MCP `instructions` field, since Claude Code cuts a server's `instructions` at 2,048 characters and the prompt is about 66 KB. Every tool call, the built-in AI's included, waits for the tool before it to finish instead of being refused. A call that arrives with no reply open begins a reply and ends it when the tool finishes. One that arrives during the built-in AI's reply belongs to that reply, and a call never ends a reply it did not begin, so a chat reply that starts while an MCP call runs takes over the rest of that call's changes.

The route also lists tools that only an outside AI gets, since they are not in the editor's tool registry: `read_system_prompt`, and a tool for each thing the Import and Download tabs do with files, `asset_import_from_file`, `asset_import_material_from_files`, `download_world_to_file`, and `replace_world_with_file`, plus `asset_download_source_to_file` for a model's original file (`MCP_ONLY_TOOLS` in `mcpTools.ts`, next to the route). The AI chat has tools of the same names that use files in its sandbox instead. The Assets tab needs none, since `asset_search` and `asset_download` do what it does. A file on the AI's computer cannot reach the editor through a tool call: it would go through the model's tokens, and Vercel limits a request to 4.5 MB. So a file tool checks that the editor answers, then replies with a curl command for the AI's own shell, which sends the file straight to the same editor route the tab uses, with the game's invite. Uploads name the session `mcp`, so each is one undo step of that session, like an upload from a tab, rather than a reply.

## Code layout

- `src/editor_sync.rs` implements shared snapshots, broadcasts, and browser edits using the types in `game_types/src/editor_sync.rs`.
- `src/endpoints.rs` contains sync, playtest, browser tool result, and Rust tool endpoints protected by `require_editor_access`; Node's browser routes use `requireEditorAccess`.
- `src/editor.rs` owns browser edit and AI tool execution, saving, chat-status reports, screenshots, user playtests, and direct game-settings handlers.
- `shared/src/api/protocol_for_chat/client_editor_tool_handlers.rs` defines `ClientEditorToolHandlers`, the tool implementations registered by the editor server for the shared registry.
- `src/database.rs` holds every database call the editor makes.
- `src/asset_uploads.rs` turns an uploaded model, image, or sound into the data an asset publish takes.
- `src/main.rs` starts Rust and its Node child and coordinates shutdown and final saves.
- `node/src/endpoints.ts` contains browser chat endpoints and authenticated `/local-only/` script diagnostics for Rust. `node/src/helpers/` contains authentication, AI SDK chat, persistence, script diagnostics, the AI chat's tools and subagents (`chatTools.ts`), and the sandbox connection (`linuxSandbox.ts`).

## Deploy

1. Review migration `0042_browser_editor.sql` and the corresponding Drizzle schema. Apply it through the website's existing `npm run drizzle-migrate` workflow. No migration is applied by building this code.
2. Configure the [website hosting API](../../packages/website/README.md#editor-hosting-api). It supplies the game id when opening an editor.
3. Build the combined Node/Rust container with `docker build -f packaging/editor-server/Dockerfile -t <image> .`, publish that image, and configure a separate Edgegap application. `scripts/configure_editor_edgegap_version.sh <version> <tag>` creates its version. Set `EDGEGAP_IMAGE_NAME` to the editor image when using that script. The image includes Node, the API dependencies, the default world, and the script declarations.
4. Put the editor's secrets, which [README_SECRETS.md](../../README_SECRETS.md) lists, in Infisical's Production `/vercel`, which syncs them to the website's Vercel environment variables. The website passes them to each editor it starts as hidden variables, so they are never in git, in the image or on the Edgegap version. `SUPABASE_URL` comes from `packages/website/.env`, the same project as the website. Reuse the same `EDITOR_SERVER_SECRET` on both services. `SITE_URL` and `AWS_REGION` come from that file too. Edgegap supplies `ARBITRIUM_REQUEST_ID`, `ARBITRIUM_DELETE_URL`, and `ARBITRIUM_DELETE_TOKEN`; allocation supplies `GAME_ID`.
5. Deploy the website. It uses its own `/api/edgegap-editor/start-editor-server/:gameId` route to open an editor, then uses the returned `editor_url` for Rust and `chat_url` for Node. Both URLs come from Edgegap's deployment status; no extra database field is needed. Desktop playtest links contain `mode=playtest`, `public_ip`, `port`, and `join_token`; the desktop connects directly to that address.

Deploy the website and the combined editor image together. Existing editor deployments must finish and close before switching container images.

`editor` is HTTPS via Edgegap's WS/TLS port on Rust port 8080; `chat` is a second WS/TLS port on Node port 8081. Both must be configured on the Edgegap version. `gameport` is UDP on port 5000 and is only bound while a user playtest is running. AI playtests use private local ports. The browser never receives worker credentials.

If Node exits or the container receives SIGTERM, Rust stops accepting browser work, cancels chat and tools, saves the world, and lets Node finish chat persistence before closing it. Rust then removes its deployment's database records and calls Edgegap's [self-stop endpoint](https://docs.edgegap.com/docs/api/dedicated-servers#self-stop-deployment) using the injected URL and token. This requires no website shutdown endpoint or account API key in the container. Website lifecycle webhooks and status checks when opening an editor repair cleanup after a crash.

For dev mode, run [`./scripts/run_website.sh`](../../scripts/run_website.sh); see the [dev website setup](../../packages/website/README.md#dev-website-and-editor). The website starts Rust with `--dev` and a unique URL prefix as games are opened. Rust starts Node on port 8081 with the same unique URL prefix. Dev shutdown saves game and chat data without accessing hosted deployment records or calling Edgegap. Losing the parent process also shuts down the dev editor.

## AI chat tools: Linux sandbox and subagents

The AI chat gets Rust's registry tools plus tools of its own from Node, `CHAT_ONLY_TOOLS` in `node/src/helpers/chatTools.ts`. An outside AI never gets these; see [Which AI gets which tools](#which-ai-gets-which-tools).

- `sandbox_run_command({ command, timeout_seconds })` runs a shell command in the editor's Linux sandbox and waits up to the 1 to 600 seconds the AI picks. A command still running then is stopped, and its output so far comes back with `is_timed_out`. `sandbox_view_image({ path })` shows the AI a PNG from the sandbox, such as a Blender render. The sandbox has headless Blender 4.3 and Python with numpy and Pillow, and the tool's description carries the advice for modeling with them.
- `asset_import_from_file`, `asset_import_material_from_files`, and `asset_download_source_to_file` move files between the sandbox and the editor. They take the same arguments as MCP's tools of the same names, with paths in the sandbox, and use the same routes under `/local-only/` (see the routes above).
- `subagent_run({ prompt })` starts a subagent and waits for its report, and `subagent_message({ subagent_id, message })` continues one started earlier in the same reply. A subagent runs in the same harness as the AI chat's reply, compaction included, with the reply's model, the same system prompt after a note of its own, and every tool except those in `TOOL_NAMES_SUBAGENTS_DONT_GET`: `subagent_run`, `subagent_message`, `publish`, and `catalog_item_publish`, which it can't reach through `run_parallel` either. Subagents share the reply's world, sandbox, and credits: their model calls are charged to the reply, and their tool calls update the reply's list of changed objects. A subagent's conversation lives in memory until the reply ends, and stopping the reply stops its subagents and their commands.

Tool calls in one step run one at a time, in the order the model wrote them, except that subagent calls next to each other run at the same time. Each subagent keeps its own order, so it never waits for the AI that started it, and Rust's tool lock still runs one Rust tool at a time for all of them.

The editor keeps one sandbox for as long as it runs, opened when a tool first needs it, so its files stay between replies and are shared with subagents. A sandbox that stops, for example when its worker crashes, is replaced on the next call without its files, and the editor closes it at shutdown. Node talks to `linux-sandbox/`'s worker over stdin/stdout, without another server or endpoint (`node/src/helpers/linuxSandbox.ts`). Requests run at the same time, so each carries an id that its reply repeats: `run`, `stop_run`, which Node sends when a call is stopped, `read_image`, `read_file`, and `write_file`. Files survive between commands; background processes end with the command that started them, and shell variables and working-directory changes do not carry over. A stopped command, and one past its timeout, is killed with everything it started, and the workspace keeps its files.

Rust saves each published model's `.glb` as its source in the private S3 bucket, as `blender/<blender_id>`, beside the `.blend` files kube.new's older Blender tools saved. Its `blender_metadata` row says which of the two it is, and the model asset's `DehydratedGltf.blender_id` refers to it. Rendering only fetches the runtime meshes and textures under `data/`.

On Edgegap, the worker and every command it runs, Blender included, run inside the **same editor deployment**. The worker clears its environment, drops privileges, restricts files with Linux Landlock, and blocks network sockets, process-group escape, and cross-process memory access with seccomp. Fork/exec is allowed and restrictions are inherited. Installed tools/libraries are readable; writes stay inside a bounded 64 MiB workspace. Python includes numpy and Pillow. No Docker daemon, nested container, VM, or additional Edgegap deployment is needed in production.

Address space is limited per process, and commands run at the lowest CPU priority; process count and file sizes are also bounded. A watchdog checks aggregate resident memory and stops the command using the most when the sandbox goes over, but this is not an independent cgroup memory quota: rapid allocations can overshoot between checks and resource exhaustion can affect the editor. This shares the kernel and container; it is not VM isolation. Missing required sandbox capabilities fail the tool rather than running unrestricted commands.

When the worker exits or crashes, the watchdog kills every process in the worker's session and deletes its workspace. Each command runs in its own process group in that session, and sandbox children can leave neither. The watchdog remains alive after worker SIGKILL, so cleanup does not depend on the worker. File reads and writes reject symlinks in every path component, traversal, FIFOs, and oversized files. GLBs are checked for external resources, cyclic graphs, and excessive geometry/images before import. Saved `.blend` files are generated content and must also be reopened inside the sandbox.

For dev on macOS, start Docker Desktop and run `./scripts/build_linux_sandbox.sh` once (again after changing the worker). Then use `./scripts/run_website.sh` normally. The editor starts a Linux container with the same worker the first time the AI chat uses its sandbox, and removes it at shutdown; Docker is only needed for the sandbox tools. Edgegap does not run nested Docker. Linux dev currently requires the same root launcher, Blender installation, Landlock support, and bounded `/dev/shm` as the production image.

The dev image explicitly starts the worker with `--isolated-container`: Docker isolates its filesystem, so Landlock is not required inside that image. The launcher supplies no editor credentials or host mounts, disables networking, makes the root filesystem read-only, and bounds memory, CPU, processes, and workspace storage. Privilege dropping, seccomp, worker limits, and cleanup still run. The default worker always requires Landlock; production never switches modes because a kernel feature is missing.

Run `cargo test -p linux_sandbox --test validation` for model file validation without external services. After building the dev image, run `npm run test:sandbox` in `crates/editor_server/node/` on macOS to test Docker isolation, stopping a command, and container cleanup using the worker's existing security checks. The production Landlock tests run with `docker build --target sandbox_tests -f crates/editor_server/linux-sandbox/Dockerfile .` on a kernel with Landlock support; they cover Blender rendering, reopening saved sources, file reads and writes, stopped commands, and descendant cleanup after worker crashes. GitHub Actions runs them on every push that changes the sandbox (`.github/workflows/sandbox-tests.yml`). These tests do not upload assets. A full modeling/upload test additionally uses Bedrock and Supabase.

## Persistence and lifetime

- `game_editor_worlds` stores the unpublished world. First open seeds it from the game's latest published version or the original default world. Every completed tool saves it; shutdown saves it again. `publish` still creates a `game_worlds` version and thumbnail. These operations use direct Rust calls without serialized request/response wrappers; ownership, world, and PNG validation remain in the publishing functions.
- `starting_editor_servers` / `running_editor_servers` use game-row locking, atomic promotion, scoped cleanup, and polling of Edgegap deployment status. Cleanup for an old deployment cannot remove a replacement runtime.
- `chat_messages` stores AI SDK messages, checkpointed while streaming. `chat_usage` has one row per model call, linked to its reply by `message_id`.
- Rust and Node reach the database only through PostgREST, with the service key, so an editor holds no database connection. Rust's every operation is in `src/database.rs`, over `shared::postgrest`, and Node's is in `node/src/helpers/database.ts`, over Supabase's `@supabase/postgrest-js`. Whatever has to happen in one transaction, such as a save that checks this editor is still the game's editor, is a database function in `0092_editor_database_functions.sql`. A function raises `sqlstate 'PT<status>'` for an error meant for the user, which reaches the browser with that status.
- The website's `createGame` action saves the homepage prompt in `chat_messages` in the same transaction as the new game. The browser submits that saved message once the editor is ready. Manual creation starts with no messages.
- A game has one active reply at a time: only one editor runs per game, and its Node process refuses a second reply while one runs. That game's Node process keeps its cancellation controller in memory. After a crash, a reply keeps whatever was saved; uncertain tools are never replayed automatically.
- World state arrives as an initial snapshot and streamed changes; it is never periodically polled. Refreshing rejoins the same editor and reads saved chat progress. It does not replay old stream chunks.
- Playtest join tokens live only in that playtest's memory. The QUIC handshake validates and consumes them once. Each Add player link spawns a separate desktop process. Stopping the server closes its players and invalidates old links. Normal Play retains its single-instance behavior.
- In dev, `/playtest/add-player` launches the sibling `client` executable directly with `--open-separately` and the same playtest link, then returns 204. `run_website.sh` builds both executables. Hosted editors return `launch_url` for the browser to open through the installed app.
- An editor pauses after fifteen minutes with no activity, and after fourteen hours in any case. Activity is anything a person does in an editor tab (the page reports it on its world socket at most every 30 seconds), an AI reply, a running tool, or players in the user playtest; the fifteen minutes start when the last of these ends. Pausing is an ordinary shutdown that also closes every world socket with its reason, which the browser shows with a Start editing button. [Edgegap cloud deployments still have a 24-hour limit](https://docs.edgegap.com/learn/orchestration/deployments.md#id-5.-deployment-stopped). Unlimited lifetimes require Private Fleets with persistence enabled.

## Checks

In `node/`, run `npm run format` to format Node source and tests with Prettier. `npm run check` checks formatting and TypeScript. Formatting uses four-space indentation, single quotes, no semicolons, and a 100-column target.

`npm run check` and `npm test` in `node/`; `cargo test -p editor_server --test auth_tests`; website typecheck/build; `cargo test -p server --test playtest_auth_tests`; `cargo test -p shared --test browser_editor_tools`; `cargo test -p client --test playtest_deep_link_tests`.

Deployment verification requires the configured services: open a new game, make an AI edit, refresh, capture a screenshot, start a user playtest and add two players, stop/restart it, and check that the old link fails and both old clients close. Also verify an AI headless playtest and publication without replacing the user's playtest. Local checks do not launch servers or mutate hosted data.
